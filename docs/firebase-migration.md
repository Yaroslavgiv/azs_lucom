# Смена Firebase без смены сценариев

Перенос на другой backend не входит в версию 1.3. Ниже порядок, которым его можно выполнить позже, не меняя экраны.

## Что выгружается

- Firestore: станции, заявки, ТО, профили, оргструктура, справочники, правила договора, аудит, уведомления.
- Идентификаторы: локальный числовой `requests.id`, UUID новых сущностей, пары `sync_map`.
- Вложения пользовательского сценария нет, поэтому бакет Storage в перенос не входит.

## Как устроен клиент

UI пишет в SQLite. Репозитории ставят операции в очередь. `SyncService` — единственное место, которое знает про Firestore. Команды смены статуса принимает `applyWorkCommand`, а не прямой `update` защищённых полей из клиента.

Чтобы подключить другой backend, заменяется реализация транспорта очереди и чтения панели. Контракты `packages/azs_domain` и локальная схема при этом остаются.

## Порядок переноса

1. Остановить приём новых команд на время снимка.
2. Выгрузить коллекции Firestore в промежуточный формат с теми же полями, что в SQLite.
3. Загрузить снимок в целевое хранилище, сохранив `uuid`, номера станций и ревизии.
4. Переключить транспорт синхронизации на новый адаптер.
5. Сверить количество станций, открытых заявок и ТО текущего месяца.
6. Вернуть приём команд и проверить одну фиксацию ТО и одну заявку.

Service account JSON в репозиторий не помещается. Учётная запись Apple Developer для сборки iOS остаётся обязанностью заказчика, см. [delivery.md](delivery.md).
